# 打分与组餐规则（Scoring Rules）

> 与 `scripts/build_pool.mjs` 一一对应。
> 网页 Demo **不另存一份**：`assets/demo.html` 里的引擎段由 `scripts/sync_demo.mjs`
> 从 `build_pool.mjs` 整段注入，`node scripts/sync_demo.mjs --check` 可判定是否同步，
> 且已纳入 `validate_skill.mjs` 自检。手工同步曾经分叉过两次，不再手工同步。

## 0. 三条铁律（优先级从高到低）

```
用户偏好（硬过滤）  >  预算合规（硬上限）  >  三卡差异化（软优化）
```

任何情况下，上一级都不为下一级让路。这条规则是踩了十几个坑之后定下来的，见 `workbuddy.md` 的调试记录。

### 0.1 排序的第一顺位：钱

三张卡的候选排序里，**"要不要用户多掏钱"排在主题分之前**：

```js
const aOver = a.total > 用户预算 ? 1 : 0;
const bOver = b.total > 用户预算 ? 1 : 0;
if (aOver !== bOver) return aOver - bOver;   // 预算内永远优先
if (全部候选都超预算) { /* 按超支比例分档（每档 15%），档内按主题分 */ }
return b.score - a.score;
```

这条是硬写死的，因为反面教训太贵：曾经主题分把一张超支 ¥11.4 的四件套排在了一张 ¥40 的二件套前面，
理由只是"四件套更像一顿完整的饭"（`diversityBonus`）。用户对钱的敏感度远高于"三张卡长得不一样"。

### 0.2 差异化必须发生在同一价格档位内

`nearTop`（用于挑"不同"的那批候选）额外要求 `|总价 − 最优总价| / 最优总价 ≤ 10%`。
否则"分数差 ≤10"在超预算候选上很容易成立（便宜的组合往往因为份量小、完整度低反而分低），
差异化就会绕开预算约束——实测预算 ¥30 时豪爽卡落在 ¥51.9，而 ¥31 的合规组合就在旁边。

### 0.3 三张卡不许重样，哪怕预算很紧

性价比卡的定义是"三张卡里最便宜"，但只保证这一点还不够：
预算紧到只剩一个解时，豪爽型和性价比型会拿到同一份菜单（实测预算 ¥30 时两张卡都是 ¥31）。
用户看到的不是"殊途同归"，而是"程序出错了"。所以终局还有一道校验：
撞车的卡在自己主题的候选池里换一个主食，**同价位、不同东西**就比重复强。

### 0.4 主题标签不许说谎

豪爽型的热量不得低于其它**有热量数据**的可比卡。曾经出现过豪爽卡 485 kcal、
性价比卡 633 kcal 的情况——"豪爽"如果连热量都输，这个标签就是骗人的。
但换"更猛"的组合**不许顺带涨价**：只允许在"不比当前这张贵"的候选里换，
否则就是用多花钱去换更猛，双输。

## 1. 单品基础分（满分 100，只用于底线排序）

```
itemScore = budgetFit(25) + flavorFit(25) + spiceFit(15) + fullnessFit(15) + healthFit(10) + novelty(10)
```

| 维度 | 权重 | 计算规则 |
|---|---:|---|
| `budgetFit` | 25 | 价格 ≤ 人均预算：`12.5 + 12.5 × (1 − price/(budget×2))`；超预算 20% 内给 10；再往上 0 |
| `flavorFit` | 25 | 命中风味派系 25；`flavor=any` 时统一 20；完全不相关 5 |
| `spiceFit` | 15 | `none`→不辣 15 / 带辣 0；`mild`→带辣 12 / 不辣 10；`hot`→带辣 15 / 不辣 6 |
| `fullnessFit` | 15 | `light`→小/中份 15，大份 6；`normal`→统一 15；`heavy`→大份 15 / 中份 10 / 小份 5 |
| `healthFit` | 10 | 仅 `careCalories=true` 生效：`10 × 全菜单最低kcal / 该项kcal`，无数据时健康向餐品 9、其他 4；否则统一 5 |
| `novelty` | 10 | 命中「新品 / 限定 / 当季 / NEW」10，否则 5 |

**份量判定**（`sizeOf`）：先看 tags（大份/双层/巨无霸/安格斯 → large；小份/迷你 → small），
**tags 为空时用热量兜底**（主食 ≥520 kcal 算 large、≤320 kcal 算 small；非主食阈值 380/200）。
真实门店数据里 tags 经常是空的，只看 tags 会让"大小份"全部退化成 normal，豪爽型就失去了判断依据。

## 2. 三主题目标函数（差异化真正的来源）

三张卡**不是同一套算法取前三**，而是三个不同的目标函数。注意它们都不再依赖 `flavorFit`
——风味已经在第 3 步做了硬过滤，这里再算一遍只会把三张卡推向同一个答案。

### 豪爽型（Hearty）— 只看"够不够猛"

```
score = 0.30×budgetFit + bigBoost + kcalBoost + richnessBoost

bigBoost      = 大份 +34 / 小份 −30 / 其余 0        （仅主食权重全量，配餐减半）
kcalBoost     = min(26, kcal / 26)
richnessBoost = 主食命中「双层|巨无霸|厚牛|安格斯|三层|加大」+8，「牛|培根|芝士|吉士」+4
```

### 清爽型（Fresh）— 轻负担优先

主食池先做三层收紧（每层都"非空才采纳"，绝不清空食物池）：

```
1. 剔除辣味主食
2. 剔除去皮油炸类（薯条 / 炸 / 鸡块 / 鸡翅 / 麦辣）
3. 只保留热量不超过中位数的主食
```

```
score = 0.30×budgetFit + healthyBoost − friedPenalty − spicyPenalty − kcalPenalty

healthyBoost = 命中蔬果/无糖/矿泉水/纯茶/低脂 +22
friedPenalty = 油炸类 30
spicyPenalty = 辣味 22
kcalPenalty  = min(28, kcal / 30)
```

### 性价比型（Value）— 钱要花得值

```
score = 0.45×budgetFit + priceRatio×22 + valueRatio×9

priceRatio = 1 − 该项价格 / 全菜单最高价
valueRatio = min(3, kcal / 价格)      // 同样价钱给得更多，才是性价比
```

## 3. 组餐流程

```
1. 用户偏好硬过滤（spice=none 剔除辣味；flavor≠any 只约束主食桶）
2. 每个主题各自给自己的主食排序（清爽型额外做三层收紧）
3. 配餐桶候选：每桶"主题 Top3 + 最便宜 3 个"（去重后通常 6 个以内，控制组合爆炸）
4. 穷举组合：mainFood × side × drink × dessert（用户说不要的桶直接跳过）
5. 预算硬上限 cap = 人均预算 × 人数 × ×1.1
6. 预算紧（主食吃掉 cap 的 70% 以上）时，额外生成"三件套 / 两件套"精简组合，
   两件套一律用各桶最便宜的一款，避免为了保饮料而让主食降级
7. 组合分 comboScore = 单项均分 + (覆盖桶数−1)×4 + 预算占满率×4
   ——"完整度"是加分项，不是硬门槛；预算不够时宁可少一样
8. 只在 cap 内的组合里挑；若全部超预算，按"离预算最近"排序（不是最便宜）
   并先截断掉"离谱的贵"（主食单价 > 最便宜主食 + max(20, 预算×0.5) 的直接剔除）
```

### 差异化策略（软，且必须让步于预算）

```
1. 优先：主食不同 且 整体清单不同
2. 次选：整体清单不同（主食相同，靠配餐区分）
3. 兜底：本主题最优
限制：只在"比本主题最高分低 ≤10 分"的候选里做差异化；
      且若差异化选项会超预算、而最优选项不超，则放弃差异化。
```

### 预算超支必须明示

| 状态 | 触发条件 | 文案 | 上限 |
|---|---|---|---|
| `inBudget` | 总价 ≤ 用户预算 | 「预算内」 | — |
| `stretch` | 用户预算 < 总价 ≤ 预算×1.3 | 「⚠️ 略超预算 ¥N」 | 预算 ×1.3 |
| `overAll` | 连 cap 内都没有组合 | 「⚠️ 预算不够（超 ¥N）」 | 不封顶，但已剔除离谱项 |

**基准永远是用户报的预算**，不是内部放宽 10% 的容差。用户说 30 块、账单 32 块，就得说"超了 2 块"。

## 4. 输出格式

```json
{
  "theme": "hearty",
  "label": "🗡️ 豪爽型",
  "items": [
    {"code": "M004", "name": "麦辣鸡腿堡", "bucket": "mainFood", "qty": 1, "price": 22.5, "subtotal": 22.5, "kcal": 520}
  ],
  "estimateTotal": 49.5,
  "totalKcal": 1130,
  "kcalComplete": true,
  "budgetCap": 50,
  "budgetStatus": "inBudget",
  "overAmount": 0,
  "note": "预算内",
  "score": 62.4,
  "reason": "麦辣鸡腿堡 打头，配薯条(大)、可口可乐(大)，饱腹感拉满；饿了就别客气。"
}
```

**`reason` 必须引用真实餐品名**，禁止「综合评分最高」「为您精选」这类空话。

## 5. 边界情况

| 情况 | 处理 |
|---|---|
| 某桶只有 1 个餐品 | 正常使用，不做多样性约束 |
| 主食桶被偏好过滤到只剩 1 个 | 三张卡共用这一款，靠配餐区分；不为了好看去编造选项 |
| 全部超预算 | 按"离预算最近"取，剔除离谱的贵项，文案标注实际超出金额 |
| 用户说要饮料但预算放不下 | 降级成"主食 + 小食"，而不是把预算全砸在饮料上 |
| 无营养数据 | `totalKcal` 为 `null`；部分缺失时只累加已知项并置 `kcalComplete=false`，**绝不估算** |
| 人数 > 10 | 提示「人数较多，建议看团餐或分单」，不强行生成 |
| 无法分桶的餐品 | `detectBucket` 返回 `null`，直接丢弃——**不猜** |
| 售罄餐品 | `normalizeMenu` 阶段就剔除，绝不进入候选 |
